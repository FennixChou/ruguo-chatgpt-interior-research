0. 結論先行

  1. ChatGPT（Images 2.0／gpt-image-2）做「平面圖→立體圖」已經堪用在溝通，做「平面圖→施工級立面圖」還不行——立面線稿畫得出來，但尺寸數字是裝飾性的，來源自己承認 [S09]。同一來源的三家逐項評等裡，ChatGPT 的「Geometry that matches the plan」判定是 No、「Editing a plan without redrawing it」判定是 Drifts（見 §2-1 開頭表），所以「堪用」指的是客戶溝通，不是幾何正確。
  2. 最大風險：手上最好的 prompt 幾乎都不是在 ChatGPT 上驗證的。 十二路研究員產出的 68 條逐字 prompt 裡，明確標示跑在 gpt-image-2／Images 2.0 上的只有 7 條，其中「平面／藍圖為輸入＋明確標示 ChatGPT 現行世代」者共 3 條（[S11]、[S14] 標 gpt-image-2；[S15] 標 Images 2.0），而 [S15] 那條從頭到尾沒有任何格局鎖定語。其中 42 條完全沒標模型版本，另有 19 條標的是 4o／DALL·E 3／gpt-image-1.5／Gemini 等非現行 ChatGPT 世代。 老闆指名的兩站把這個風險放得更大：archi-prompt.com 逐字取得的 165 則裡 130 則（79%）自標 Nano Banana（新增 134 則中為 103 則／77%），精確標「gpt-image-2」的是 0 則 [S64]；建築學長全站只取得 1 條逐字 prompt，且不是 ChatGPT 導向 [S68]。合計本報告手上共 234 條逐字 prompt（68＋165＋1），標明現行 ChatGPT 世代的仍只有那 7 條。抄來的句子第一次用一律當試辦，不當定論（賈維斯判斷）。
  3. 本輪最值錢的一句話是「match clause」：不要只說「轉成 3D」，要逐項複述哪些幾何必須保留（房間位置、門窗開口位置、相對牆長），否則模型會「重畫」而不是「轉換」[S09]。這一條和 8/19 基線的 [LOCK] 硬鎖句方向一致，等於被外部來源背書一次。
  4. 視角要給數字，不要給名詞。 寫 about 45 degrees above the floor 勝過寫 isometric；寫 ceiling removed 勝過寫 cutaway；寫 knee height walls 勝過寫 low walls——因為模型常把 isometric 當成一種畫風而非投影法 [S09]。
  5. 要「真立面／真剖面」就必須寫死 flat orthographic, no perspective，否則網路上九成的「立面 prompt」出來的其實是透視效果圖 [S12]；本輪逐字查核了 walk-in closet 8 條（全部指定 wide-angle／eye-level）[S32] 與 TV wall 一整頁（含 LED 氛圍光的 3D 效果圖）[S33]，無一條是正投影。老闆指名的 archi-prompt.com 補上的是半塊缺口，不是整塊：該站「建築圖表｜室內圖表」系列有一則室內正投影立面展開圖（四面牆攤平成一列、含基準線與尺寸串、結尾 no shadows, no perspective, no photorealism；但該則站內分類是「室內設計／文生圖」、input\_type 為 text-only，全文沒有「以上傳平面圖為幾何依據」的輸入宣告，也沒有 match clause）[S53]，與一則照片轉家具立面圖紙（Revit 風格、含尺寸線圖框；原文未出現 orthographic／no perspective 任何鎖定語）[S54]。所以正確說法是：「平面圖→室內正投影立面」仍然沒有現成原版可抄，只有 1 則純文生圖的正投影室內立面＋1 則照片轉家具圖紙，C 模式證據等級維持在「有圖面語彙可抄、無對題原版、未在 ChatGPT 驗證」（見 §4 C）。
  6. 官方自己列了兩條對我們最傷的限制：文字放置與清晰度仍會出錯、以及「在結構化／版面敏感的構圖中難以精確擺放元素」[S03]——平面圖正是最典型的結構化構圖。這句話應該直接寫進給客戶的免責說明。
  7. 先分析、再生圖仍然是唯一有實測背書的做法，本輪拿到它的英文版 [S09] 與學理支持 [S38][S39]；升級點是第一段輸出改成結構化條列（房號／用途／相鄰關係），比純文字複述更準 [S40]。
  8. 8/19 之後官方最重要的兩個變化：Images 2.0 於 2026-04-21 發布，單一 prompt 可產最多 8 張風格一致的圖 [S01]；2026-08-30 起 DALL·E GPT 在 ChatGPT 內退役，生圖只剩 ChatGPT Images 一條路 [S08]。這兩頁本輪都被 Cloudflare 擋下、內容取自搜尋摘要重建，非直讀原頁（需確認，見第 10 章來源表），所以基線「多視角一致性」只能升級為「疑有官方能力背書（來源未直讀，需確認）」，實測前不得對客戶宣稱。
  9. input_fidelity 參數對我們可能已經沒有意義——官方 API 指南（此句屬研究員摘要，逐字段未收錄，需確認）指出它只適用 gpt-image-1.5，gpt-image-2 不可調（自動高保真）[S03]。基線待辦第 9 條「參數對帳」要刪掉之前，先由人工開頁確認一次。
  10. 建議動作分三層：現在就做四項——A 等角切頂俯視／E 保格局換風格／F 局部修改／B 單空間透視，全部沿用既有管線只換鎖定語；試辦九項（優先序，與第 9 章一致）——提案與樣品屋陳設工作流（本輪新增，證據最實用，第一順位） → 兩段式結構化第一段 → 標籤英譯表 → D 剖面軸測 → 多視角一次出 → ChatGPT vs Nano Banana 對照 → C 立面 → archi-prompt 列入常查清單（免費，不訂閱） → JSON prompt；不建議四項——AI 立面當施工圖／買付費 prompt 包／讓 AI 在圖上寫中文／訂閱建築學長付費版（除非要做競品實測）。明細與停損見第 9 章。
  1. 老闆指名兩站的一句話結論：archi-prompt.com＝值得加進常查清單、不必付費——站方公開 API 可逐字讀到 6,424 則提示詞，本輪取樣 165 則，室內軸測／虛擬軟裝／圖面語彙三塊直接補到如菓的缺口（室內立面只補到「有語彙、無對題原版」，見結論 5），但 79%（130／165）標 Nano Banana、gpt-image-2 精確標示 0 則，一律要在 ChatGPT 重測 [S64]；建築學長（jianzhuxuezhang.com）＝目前不建議常看——93 個工具裡有 6–7 個與「平面圖轉 3D／立面」逐字對應，但幾乎全鎖企業版與登入牆（「93 個工具」與「幾乎全鎖企業版」兩項僅來自該次 Chrome 人工直讀、無法二次覆核，需確認），本輪只拿到功能描述與三份公開詞庫（風格 234／材質 490／色彩 218，皆為去空白後筆數），拿不到任何官方逐字 prompt，且官方工具目錄查無「GPT」字樣、只綁 Gemini Banana Pro，與其知乎「GPT-image-2 上線」宣稱有出入（列疑點、不下定論）[S65][S66][S67]。細節見附錄 B。

  2. Gemini is currently the more literal of the two when you attach an existing plan, and ChatGPT is the better reader and planner when you want the plan described rather than drawn.（FAQ「Can ChatGPT or Gemini actually draw a floor plan to scale?」段末——注意後半句對 ChatGPT 是正評：讀圖與規劃它較強）。

這張表怎麼用：本報告的 A／B／F 模式語彙大量取自 [S09]，但同一來源對 ChatGPT 的判定是「幾何對不上（No）」「改圖會漂移（Drifts）」。所以下面「能做」各點，指的是在 match clause 把誤差壓小之後、供人看的溝通圖，不是幾何正確的圖。第 9 章的可行性評等已依此下修。

2-1　能做（每點附來源）

  • 等角切頂俯視（doll-house）圖，是 ChatGPT 相對最穩的一類——前提是 prompt 裡逐項複述要保留的幾何 [S09]。但同一來源對 ChatGPT 的 Geometry that matches the plan 判定是 No、doll-house 只給 Good（Nano Banana 才是 Best）[S09]：格局貼近是靠 match clause 把誤差壓小，不是模型會對，每張仍須人工逐項核房間數、門窗位置與相對牆長。
  • 生圖前先讓它「讀圖覆述」：要求它列出每個房間與大約尺寸、每扇門的開向、每扇窗在哪面牆、以及看不清楚的地方，十秒內就能抓到誤讀，不必等出圖十次才發現 [S09]。
  • 一次產出多張風格／物件一致的圖：官方公告（本輪未能直讀原頁，內容取自搜尋摘要，需確認）指出單一 prompt 最多可產 8 張角色／物件／風格連貫一致的圖像 [S01]。
  • 2K 是標準解析度，API beta 支援 4K；長寬比支援 3:1～1:3，原生支援 16:9／9:16 [S01][S03]。
  • 多輪迭代編輯：這是 API 行為——官方文件講的是 Responses API 的 image generation tool，用 previous_response_id 或前一張圖的 image id 接續精修 [S04]；ChatGPT App 內沒有這兩個參數，對應的操作只是「在同一串對話裡接著講」，效果類似但不是同一件事，寫進客戶文件時不要說成「可指定圖片 id」。
  • 雙圖分工：官方說明「一張定內容、另一張定風格／佈局」，並要求依序標明每張圖的角色 [S02][S05]——這正好對應「平面圖定佈局＋風格參考圖定調性」。（[S02] 此段屬二次抓取被 403 擋下後的搜尋重建，需確認；[S05] 為逐字直讀。）
  • 正投影平面圖上材質（不轉 3D）：把平面圖渲染成有材質、有陰影但仍是正俯視的「presentation plan」。兩家來源都提供完整逐字 prompt 且互相印證，是本輪最容易上手的一類 [S09][S10]；但兩者皆為工具商內容、無前後對比圖，如菓實測前列為「聲稱可行、未驗證」。（原「局部編輯：ChatGPT 內的遮罩以 prompt 為主」一點已移到 §2-2 並修正——那是 API 的 mask 行為，不是 ChatGPT App。）

2-2　不能做（每點附來源）

  • 不是可旋轉、可量測、可匯出的 3D 模型（8/19 基線既有結論，本輪無反證）。
  • 結構化構圖是官方自承的弱項：「Despite improved instruction following, the model may have difficulty placing elements precisely in structured or layout-sensitive compositions.」[S03] 平面圖就是最典型的 layout-sensitive composition。
  • 文字仍會出錯：「the model can still struggle with precise text placement and clarity.」[S03] 對應到我們就是房間標籤、尺寸數字會亂。而且這不是 ChatGPT 獨有——官方社群 2025-06 的討論串把 ChatGPT／Gemini／Claude 一起點名，共通肇因是「整段文字一次塞給模型」[S48]；更早一串（2025-03，legacy）另指出模型「不太理解『空白』」，你叫它留白它反而會自己塞字進去，所以備援作法是先留白框、正確文字另一步再貼 [S50]。對如菓的結論一樣：圖上不要讓 AI 寫字。
  • 立面圖的尺寸不可信：來源自己坦承這類測量是裝飾性的、數字不能當真 [S09]。
  • 空間理解仍有硬傷：PTT 轉述的評測中，GPT Image 1.5 把房間實景照還原成平面圖時完全搞錯空間配置，同題 Nano Banana Pro 正確 [S22]（legacy，gpt-image-2 是否改善需確認）。
  • 常見自作主張：門消失、衛浴門被家具擋住、憑空多出未說明的房間、走廊無中生有 [S13]。這四項與 8/19 基線的「替暗房加窗／併房切房／誤讀廚房線」互相補齊。
  • 編輯會把錯誤跟牆一樣忠實保留：[S09] 逐字——Editing preserves mistakes as faithfully as walls... a good match clause cannot tell a feature from an error. Fix problems in the plan before you start editing it. 上傳前先把原圖的錯誤修好，否則鎖得越死、錯誤保留得越完整。
  • AI 完全不檢查任何建築法規：[S09] 逐字——Nothing here is code compliant. Minimum room sizes, egress windows, stair geometry and accessible clearances are set by your local building code, and no image model is checking any of them. 最小房間尺寸、逃生窗、樓梯幾何、無障礙淨寬一律不算數，這句要進全文免責。
  • 遮罩（mask）不是 ChatGPT 對話框的功能：官方逐字說明的是 API 的 mask 參數——Masking with GPT Image is entirely prompt-based. The model uses the mask as guidance, but may not follow its exact shape with complete precision.[S03]；ChatGPT App 內框選編輯的實際行為本輪未查證，需確認，不要把 API 行為當成 App 行為。
  • 不要期待它輸出可編輯檔：DocsBot 那類「technical drawing」prompt 的輸出格式段落寫明是文字描述或 ASCII 示意，不是圖 [S24]（同站另一則剖面 prompt 亦同）；直接餵給生圖模型只會出一張沒意義的畫面。

3. 提示詞解剖：一條好 prompt 的固定骨架

八段，順序固定。這是 8/19 九 block 主模板的外部驗證版與細化版——block 名稱不變，只補「為什麼」和證據。

① 輸入宣告

寫法：第一句就說清楚上傳的是什麼、要拿它做什麼。例：Use the uploaded 2D floor plan as the authoritative geometry reference.；多圖時逐張標號說明關係。
為什麼：官方明文建議在 prompt 裡用 draw、edit 這類動詞，模型表現最好 [S04]；多圖輸入時官方要求「依序標明每張圖並說明彼此關係」[S02][S05]。Redraw 更激進，直接宣告「把這張圖當成鎖定圖層」（treat the floor plan as a locked image layer）[S10]。

② 格局鎖定（match clause）

寫法：逐項複述必須保留的東西——外框、牆位、隔間、門洞、窗洞、房間數、房間相對比例、動線、方位（有沒有鏡像）、比例尺。
為什麼：這是本輪最強的單一發現。來源的核心論點是：沒有 match clause，模型會 redraw（重畫） 而不是 convert（轉換）[S09]。Redraw 的寫法是 Preserve 100% of the original layout, wall positions, openings, structure thickness, furniture placement, circulation areas, proportions and dimensions. 並特別把 Orientation（方位） 與 Scale（比例） 單獨列名 [S10]——這是本輪唯一直接對抗「鏡像翻轉」問題的條款。學理上，PlanCraft 論文主張 2D 平面圖是「不可省略的空間契約」，先鎖平面再談陳設，等於把開放式推理收斂成有邊界的約束問題 [S38]。

③ 視角與相機

寫法：給數字，不給名詞。角度寫 about 45 degrees above the floor；切頂寫 ceiling removed；矮牆寫 knee height walls 或直接給數值 walls at about 40 centimetres；真投影寫 flat orthographic, no perspective 或 strictly in orthographic top view (no camera distortion)；透視圖寫鏡頭與站位 24mm lens at chest height, verticals straight。
為什麼：來源明講模型常把 isometric 理解成一種藝術風格而不是投影法，所以角度數字優於術語 [S09]。牆高數值還有第二個功能——刻意壓低到 40 公分，畫面會被讀成「平面圖」而不是「照片」[S09]。flat orthographic, no perspective 是目前找到最直接的「真投影」鎖定語 [S12]，Redraw 的 no camera distortion 是同義的另一種寫法 [S10]。如菓正典：眼高 120 cm、24 mm（可 20–28；特寫／招牌 35–50）、no fisheye、verticals kept straight（8/19 基線 F 段，不變）。

④ 風格

寫法：明確指定風格名，不要留白。
為什麼：坊間常引的「不定義視覺風格，模型會預設寫實」一句，本輪那次對 [S07] 的人工直讀未見此句（該頁對外回 403、無留存純文字檔可二次覆核，故只能寫「該次直讀未見，需確認」，不宜斷言「不在該頁」）；近似原句出自 OpenAI 另一頁教育電子報，本輪未直讀、需確認，因此本報告不把它當已證實依據。如菓做法不變、且不依賴這句：一律用十風格正典名（見第 5 章），沒指定先問，問不到用現代簡約並註明（8/19 基線）。同案換風格時只改這一段，其他段落一字不動，出圖差異才可歸因（8/19 基線 H-2 第 1 條；[S09] 的北歐材質版與 doll-house 版差異即是同一手法的實例）。

⑤ 材質與色彩

寫法：限五種以內（地坪／牆面／櫃體／檯面／織品各一），寫名稱不寫 hex。範例句式：pale oak floors, white walls, light stone in the bathroom, oatmeal upholstery [S09]。
為什麼：材質色票寫死可以對抗「風格幻覺與色彩漂移」[S09]。Redraw 進一步示範「單一形容詞決定成敗」——寫 matte metallic finish (not glossy) 和寫 metallic 出來的質感完全不同 [S10]。8/19 基線 H-2 第 15 條「材質先建分類表再寫進提示詞」在此得到外部佐證。

⑥ 光線

寫法：材質詞要連光一起寫；並在改圖時加燈光保護子句。範例：soft daylight, gentle contact shadows, plain light background [S09]；保護子句 Preserve the original lighting design exactly as shown in the image. Do not add new light sources, remove existing lights, or modify lighting positions. [S10]。
為什麼：8/19 基線 H-2 第 5 條說「材質的說服力來自光而不是名詞」；本輪 Redraw 把它變成可貼上的獨立子句 [S10]。另外實測回報顯示透視圖最常見的兩種漂移是「鏡頭飄高」與「窗光死白」[S09]，光線段落要主動壓制後者。

⑦ 輸出規格

寫法：講清楚要幾張、什麼比例、要不要文字。
為什麼：以下尺寸與 quality 是 API 參數（[S03]）——1024×1024／1536×1024／1024×1536／2048×2048（2K 方形）／2048×1152（2K 橫）／3840×2160（4K 橫）／2160×3840（4K 直）／auto，長短邊比不超過 3:1，quality 分 low／medium／high／auto。ChatGPT 對話框內只能用自然語言指定張數與長寬比；能不能吃 quality 或精確像素，本輪未實測、需確認——在實測前一律改寫成「輸出 1 張 3:2 橫幅、不要任何文字」（賈維斯判斷）。文字要嚴格控制：官方承認文字放置仍會出錯 [S03]，OpenAI 社群的共識修法是「要出現的文字逐行分開列，不要整段丟」[S48]（2025-06，Images 2.0 前世代；官方稱文字渲染已大幅改善但仍會出錯 [S03]，此修法仍建議沿用）；而一套線上工具的做法更乾脆——DO NOT include any text labels, text annotations, or written text. Use ONLY annotation symbols, dimension lines, leader lines, and graphical symbols. Users will add clean, proper, editable text in post-processing. [S36] 建議如菓直接採這條：圖上不放中文字，標註後製再加。

⑧ 負面清單

寫法：逐條 DO NOT，可以用大寫加強。最完整的範例是 12 條連發 [S10]；如菓另有台灣化的 AVOID 清單（壁爐／天窗／閣樓／室內樓梯／英規歐規插座／暖氣片／文字標籤／未畫的窗……，8/19 基線 F-2，不變）。
為什麼：Redraw 用 The floor plan must remain PIXEL-PERFECT identical to the uploaded image. 收尾，實測用途是阻止 AI「自作主張優化已完成的圖」[S10]。注意分工：F-1（含俯視禁令）給模式一／三，F-2（不含俯視禁令）給模式二，誤用會邏輯衝突（8/19 基線，不變）。本報告另為圖面類（立面／剖面／軸測）建了 F-3 圖面類禁令（見第 4 章共用規則），因為那類產出既不能有透視、也不能出現任何文字。

7. 工作流程 SOP：兩段式升級版

只寫 8/19 之後的增量與修正。8/19 的七步流程與五條如菓版 prompt 仍然有效，以下是疊加上去的。

新增第 0 步：先做圖面標籤英譯（Step 0）

8/19 沒有這一步。理由：本輪唯一有 gpt-image-2 標示、以平面圖為輸入的中文 prompt，成功關鍵是把原圖上每一個房間標籤逐一列進 prompt [S14]。但那是日文圖面；台灣圖面的中文標籤要先轉成 ChatGPT 看得懂的英文，否則這招在真案場圖上會卡住。本輪已自建一份對照表（主臥／次臥／前後陽台／洗衣陽台／玄關落塵區／電視牆／系統櫃／和室等 23 個詞），該表為如菓自建、非外部來源轉載，另存 台灣圖面標籤英譯對照表_zh_community_g3.md。

修正第 1 步：讀圖覆述改成結構化輸出

8/19 原本是中文自由敘述覆述格局。修正兩點：

  1. 拿到了英文版的等效寫法：Here is my floor plan. Before generating anything, list what you can see: every room with its approximate size, every door and which way it swings, every window and which wall it is on, and anything you cannot read clearly. No images yet. [S09]
  2. 輸出格式改成條列或 JSON（房號／用途／尺寸／相鄰關係／門開向／窗在哪面牆），不要自由散文。學理依據：把房間當「離散符號單位」逐一列舉，能提升模型對幾何與拓撲關係的一致性 [S40]；另一條管線也驗證「先輸出結構化 JSON、人工核對、再進 3D」的順序能顯著提升成功率 [S39]。

新增第 2 步：先出白模／技術圖層，再上材質

8/19 標為「零實測、合理推論」。本輪拿到兩層支持，但兩層的證據等級不同：①官方教學（OpenAI Academy）疑有「小幅、針對性的修改」「重複最重要的細節可以防止圖像在反覆精修時漂移」之說 [S07]——該頁對外一律回 403、只有一次人工直讀紀錄且未留存純文字檔，無法二次覆核，需確認；②學理上有論文主張把「幾何」與「風格陳設」拆開下指令，一次全塞會讓兩種推理互相干擾 [S38]——此條逐字直讀有留存。狀態從「推論」升級為「有學理支持＋疑有官方教學支持（該頁需確認），仍缺如菓實測」。

第 3 步：主 prompt 用第 3 章八段骨架

不變，只是每段現在都有外部證據（見第 3 章）。

新增第 4 步：局部修改一律走 F 模式

改一處就用 F-R1，不要重新生成整張。原則出處：editing beats generating，單一動作指令讓模型留在編輯模式 [S09]（逐字留存）；官方教學疑亦建議一次只改一項 [S07]（該頁 403、無留存，需確認）。

8. 案例精選

每張卡＝一個可學的點。「可學的一點」是賈維斯從該來源萃取的操作結論。

卡 01｜match clause 是成敗分水嶺
來源 [S09]｜2026-08-24／25｜輸入：2D 平面圖 → 輸出：3D doll-house
關鍵片段：Keep every room in the same position, keep the door and window openings exactly where the plan shows them, and keep the relative wall lengths.
可學的一點：不寫這句，模型會 redraw；寫了才是 convert。這是本輪唯一被作者明確定義為「核心關鍵」的技巧。

卡 02｜牆高數值決定畫面被讀成什麼
來源 [S09]｜2026-08-24／25｜輸入：平面圖 → 輸出：正上方俯視剖視
關鍵片段：with the walls at about 40 centimetres so the layout reads like a plan rather than a photograph
可學的一點：牆高不是寫實參數，是「畫面語言」的開關。要客戶看格局就壓到 40 cm，要看空間感才用 2.8 m。

卡 03｜術語換成人話與數字
來源 [S09]｜2026-08-24／25
關鍵片段：ceiling removed（取代 cutaway）、knee height walls（取代 low walls）、about 45 degrees above the floor（取代 isometric）
可學的一點：模型把 isometric 當畫風不是當投影法。凡是專業術語，都改寫成「怎麼看＋幾度」。

卡 04｜分區只做一區，防止模型自行擴建
來源 [S09]｜2026-08-24／25｜輸入：整戶平面圖 → 輸出：只有客餐廳的 3D
關鍵片段：Render only the living and dining part of this floor plan in 3D, cropped to that area, ceiling removed, three-quarter view.
可學的一點：整戶一次生容易多長房間；大坪數或複雜格局改成分區逐間生再拼。

關鍵片段：Before generating anything, list what you can see... No images yet.
可學的一點：這是 8/19 中文兩段式的英文版。差別在最後那句 No images yet. ——明講不要出圖，模型才不會偷跑。

卡 06｜逐一列舉原圖標籤（唯一一條中文＋gpt-image-2 標示的平面圖 prompt）

  • 驗收標準：B 組的格局軌得分不低於 A 組，且人工核對第一段所花的時間更短。
  • 停損條件：B 組的 JSON 常出現模型自行編造的尺寸（很可能會，因為模型不會量測），就退回自由敘述但保留「逐項條列」的格式。

  • 停損條件：一致性低於「分四次各自生成再人工挑」的水準，就退回分次生成。
